# Pre-Publish Security Review — History & Prehistory

Project: `/home/user/workspace/hp`
Context: single-file, fully offline HTML5 reference app (1,631 historical entities), no backend, no auth, no user data storage, ships as `dist/public/index.html`. Public repo (MIT) at github.com/tyohDeveloper/history-and-prehistory.

## Security Review Results

### BLOCK (must fix before publishing)
None.

### WARN (inform user, let them decide)
None.

### PASS
- **Dependency audit (`npm audit`)** — 0 vulnerabilities of any severity across 171 dependencies (5 prod, 167 dev, 54 optional). No Python `requirements.txt` present, so no `pip-audit` check applies (the Python code under `tools/` is a build-time content pipeline, not a shipped dependency).
- **Hardcoded secrets** — No matches for API-key/token/private-key/password patterns anywhere in the repo, including `tools/`, `scripts/`, `.github/workflows/build.yml`, `.replit`, and the built `dist/public/index.html`. No `.env` files exist in the project at all. The only hits for the word "token" are historical/archaeological content (clay accounting tokens in Bronze Age Mesopotamia) inside `tools/extensions_west_asia.py` and `tools/extensions_south_asia.py` — not credentials. `dist/` is correctly listed in `.gitignore` as a build artifact.
- **Zero-network-requests guarantee** — Verified true. `grep` across `src/` and the built `dist/public/index.html` finds no `fetch()`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, or service-worker registration. The only URLs present in the bundle are plain-text academic citation strings (e.g. `academic.oup.com`, various university/PDF hosts) rendered as ordinary `<a href="..." target="_blank" rel="noopener noreferrer">` citation links — these only navigate if a user manually clicks them; the app itself never fetches them. There are no `<link>`, `<img>`, `<iframe>`, external fonts, or preconnect tags in the artifact, so nothing loads passively either. This is reinforced by an existing build-time guardrail in `scripts/verify-build.mjs`, which already fails the build on any of `fetch()`, `XMLHttpRequest`, `sendBeacon`, `WebSocket`, `ServiceWorker`, `RTCPeerConnection`, `EventSource`, external `src=`/`href=`/`url()`/`@import` references, or a missing/weak CSP — and the current build passes all of those checks.
- **Injection / `innerHTML` sinks** — No occurrences of `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `dangerouslySetInnerHTML`, `eval(`, or `new Function(` anywhere in `src/` or the built HTML. All authored dataset text that reaches the DOM — entity `summary`, `date_note`, caveat `text`, and source `note` fields (`src/main.ts` lines ~284, 308, 444, 471) — is passed as a plain string argument into a small `el()` helper (`src/main.ts:110-119`) that uses `Node.append()` for children and `setAttribute()` for attributes. Both are safe sinks: `append()` treats string arguments as text nodes (HTML-escaped, not parsed), and `setAttribute()` does not interpret markup. This means entity content authored in the dataset cannot inject markup or scripts into the page even though it is long-form free text.
- **CORS / open endpoints** — Not applicable and not present: there is no backend, no server code, and no CORS configuration anywhere in the repo (confirmed by grep). This is consistent with the app having no server component at all.
- **Content-Security-Policy** — Present and effectively restrictive for this app's actual risk (the network channel): `default-src 'self' 'unsafe-inline'; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'`. `connect-src 'none'` blocks `fetch`/`XHR`/`WebSocket`/`EventSource` outright, which is the directive that matters most for the "no network requests" guarantee, and `frame-src 'none'` / `object-src 'none'` / `base-uri 'none'` close off framing, plugin content, and `<base>`-tag hijacking. `'unsafe-inline'` is present under `default-src` (there is no separate `script-src`/`style-src`), which is a necessary consequence of shipping as one self-contained file: the bundler (vite-plugin-singlefile) inlines the app's JS as a single `<script type="module">` with no `src`, so the browser can only execute it under CSP if inline script is allowed (no nonce or hash is used). This is a deliberate, low-risk trade-off for a static single-file app with no injection sinks (see above) — `unsafe-inline` would only matter if an attacker could get arbitrary markup into the page, which the DOM-construction pattern already forecloses. Note for future hardening (not a blocker): a SHA-256 script hash (`script-src 'self' 'sha256-...'`) could replace `'unsafe-inline'` for script execution alone, since the inline script content is static per build, but this is an optional improvement, not a gap that needs to hold up publishing.

## Summary
No BLOCK or WARN findings. The app's stated guarantees (no network requests, no data storage, no backend) all check out against the actual source and built artifact, and are additionally self-enforced by an existing `scripts/verify-build.mjs` guardrail that fails the build if they are ever violated. Dataset-authored text is rendered through safe DOM APIs with no injection sinks. No secrets exist anywhere in the repository. Dependency audit is clean. The project is safe to publish as-is.
