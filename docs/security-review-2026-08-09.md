# Pre-Publish Security Review — History & Prehistory v3.22.0.0

Project: `/home/user/workspace/hp`
Context: single-file, fully offline HTML5 reference app (1,640 historical entities), no backend, no auth, no user data storage, ships as `dist/public/index.html` (~985 kB). Public repo (MIT) at github.com/tyohDeveloper/history-and-prehistory. Prior review covered v3.15.0.0 (clean); seven releases have landed since, principally adding the `name_forms` schema field (structured alternate names, incl. non-Latin/RTL text, rendered with a data-driven `lang` attribute), a new dating method, and source-rendering changes.

## Security Review Results

### BLOCK (must fix before publishing)
None.

### WARN (inform user, let them decide)
- **`sources.json` `url` field has no schema or scheme validation before being written into a clickable `href`** — `src/main.ts` (`renderSources`, lines 485–497) sets `href: src.url` via `el()`'s `setAttribute` directly from `src/data/sources.json`. Unlike `entities.json` (governed by `schemas/entity.schema.json`), there is no `sources.schema.json` and `tools/validate.py` only checks referential integrity for sources (id existence, citation graph), never URL shape. Separately, the one place a `"format": "uri"` annotation *does* exist (`schemas/entity.schema.json:391-394`, the `links[].url` field) is not actually enforced: `tools/validate.py` builds its `Draft202012Validator` without a `format_checker`, so `format: uri` is silently a no-op (verified directly against the installed `jsonschema` library). All 549 current `sources.json` entries use only `http`/`https` (verified), and the one other data-driven `href` — the research "handoff" Wikipedia link — is fully code-generated, not data-driven, so this is not currently exploitable. But nothing in the build pipeline would stop a future dataset edit from introducing a `javascript:` URL into `sources.json`, which would execute on click since `href` (unlike text content) is a live sink. **Suggested fix:** add a JSON Schema (or a `validate.py` check) constraining `sources.json`'s `url` field to `^https?://`, and/or have `validate.py` attach a `FormatChecker` with the `rfc3987`/`format` extra so `"format": "uri"` is actually enforced where it's already declared.

### PASS
- **Dependency audit (`npm audit`)** — 0 vulnerabilities (critical/high/moderate/low) across 171 dependencies (5 prod, 167 dev, 54 optional).
- **Hardcoded secrets** — No matches for API-key/token/private-key/password patterns anywhere in the repo, including `tools/`, `scripts/`, `.github/workflows/build.yml`, `.replit`, `scripts/post-merge.sh`, and the built `dist/public/index.html`. No `.env` files exist. `dist/` is correctly excluded via `.gitignore`.
- **Zero-network-requests guarantee** — Verified true for both source and the built artifact. No `fetch()`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, `RTCPeerConnection`, or service-worker registration anywhere in `src/` or `dist/public/index.html`. The only URLs present are plain-text academic citation strings and a code-generated Wikipedia search link, both rendered as ordinary `<a target="_blank">` links that only navigate on manual click — the app itself never fetches them. This is independently enforced at build time by `scripts/verify-build.mjs`, which fails the build on any forbidden network API, external resource reference, or missing/weak CSP; running it against the current `dist/public/index.html` passes cleanly ("Build verification passed: single-file, offline-safe, XML-well-formed, within budget").
- **No persistent user data** — `scripts/verify-build.mjs` also fails the build on `localStorage`, `sessionStorage`, `indexedDB`, or `document.cookie` in the bundle; none are present. The only client-side state persisted is the calendar selection in `location.hash` (not persistent storage, not personal data).
- **`name_forms` injection safety (new since v3.15.0.0)** — Confirmed no injection sink exists anywhere in `src/` or the built HTML: no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `dangerouslySetInnerHTML`, `eval(`, or `new Function(`. The new `name_forms` rendering path (`src/main.ts` lines 339–367) builds each name form through the same `el()` helper (`src/main.ts`) used everywhere else: `document.createElement`, `setAttribute(k, v)` for every attribute (including the data-driven `lang` from `f.lang`, line 354), and `Node.append()` for text. `setAttribute` cannot be used to break out of an attribute or inject markup regardless of the string's content — non-Latin scripts, RTL text, quotes, or angle brackets in `name_forms[].name` or `.lang` all land as inert attribute/text content, never parsed as HTML. `dir: "auto"` is likewise set via `setAttribute` and is a legitimate, safe CSS/HTML directionality hint. No `format`/pattern restriction exists on the `lang` field in `schemas/entity.schema.json`, but since it never reaches a parsing sink this has no security consequence (cosmetic-only risk, not flagged as a finding).
- **Content-Security-Policy** — Present and restrictive for the risk that matters (the network channel): `default-src 'self' 'unsafe-inline'; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'`. `connect-src 'none'` blocks `fetch`/`XHR`/`WebSocket`/`EventSource` outright — the directive that directly backs the footer's "no network requests" claim — and is independently re-verified by `scripts/verify-build.mjs`'s own CSP check. `frame-src 'none'`, `object-src 'none'`, and `base-uri 'none'` close off framing, plugin content, and `<base>`-tag hijacking. `'unsafe-inline'` appears under `default-src` only because the app is bundled as one `<script type="module">` with no external `src` (vite-plugin-singlefile) and no nonce/hash is used; this is a deliberate, low-risk trade-off given there is no injection sink through which an attacker could get arbitrary markup onto the page in the first place (see `name_forms` finding above). Unchanged from the v3.15.0.0 review.
- **Tabnabbing (`target="_blank"` links)** — Checked all three call sites for such links in `src/main.ts`: source citation links (line 492-493), the Wikipedia research-handoff link (line 620-621), and the footer repo link (line 855). All three correctly pair `target="_blank"` with `rel="noopener noreferrer"`. No occurrence of `target="_blank"` without the matching `rel` anywhere in the codebase.
- **Open CORS / missing auth** — Not applicable: no backend, no server code, no CORS configuration anywhere in the repo (confirmed by grep across `.ts`/`.js`/`.py`).
- **Build-time self-enforcement (`scripts/verify-build.mjs`)** — Still intact and comprehensive: it independently re-checks (1) single-file output, (2) no external resource references, (3) no forbidden network APIs in the bundle, (4) CSP present with `connect-src 'none'`, (5) no persistent-storage APIs, (6) strict-XML well-formedness of the HTML shell, (7) no literal `]]>` in inlined script/style, (8) required test-ID coverage, and (9) a gzip-size regression ceiling. Running it against the current build passes every check.

## Summary
One WARN: the dataset's source `url` field (and, more generally, the unenforced `format: uri` annotation on the entity `links` schema) has no hard scheme constraint before reaching a clickable `href`, which is a defense-in-depth gap rather than a live vulnerability — all current data is benign `http(s)://`. No BLOCK findings. The app's stated guarantees (zero network requests, no data storage, no backend, no secrets) all check out against source and the built artifact, reinforced by an intact `scripts/verify-build.mjs` guardrail. The new `name_forms` field, including non-Latin/RTL authored text and its data-driven `lang` attribute, is rendered entirely through safe DOM APIs (`createElement`/`setAttribute`/`append`) with no reachable injection sink. The CSP is restrictive on the dimension that matters (network egress) and is independently verified at build time. All `target="_blank"` links use `rel="noopener noreferrer"`. Recommend fixing the WARN opportunistically (schema/scheme validation on source URLs) but it does not block publishing.
